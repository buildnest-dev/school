# Backend

TypeScript backend inside the Next.js app: route handlers in `src/app/api`, Prisma + SQLite for development (PostgreSQL for production), server code in `src/server`.

## Run

```bash
npm install
cp .env.example .env.local   # DATABASE_URL=file:./prisma/dev.db
npm run db:reset             # dev only: recreates prisma/dev.db and seeds demo data
npm run dev
```

Demo logins (fictional schools, development only, all use the password in `prisma/seed.ts`):
`principal@demo.test`, `teacher@demo.test`, `accountant@demo.test`, `parent@demo.test`, `platform@demo.test`, and `principal@other.test` (a second school used to test isolation).

## Multi-tenancy

Shared database, shared schema. Every school-owned table has `tenantId`. The tenant is taken only from the server-side session (`requireTenant`), never from the request. Data access for school data goes through `tenantDb(tenantId)` or an explicit `where: { tenantId }`. Cross-school ids return 404.

## Security model

- Passwords: bcrypt. Sessions: random 256-bit token in an HTTP-only, SameSite=Lax cookie; only its SHA-256 is stored.
- State-changing routes check `Origin` against `Host` (CSRF) and validate bodies with Zod.
- Login is throttled (5 tries / 10 minutes) **in memory**: a multi-instance deployment needs a shared store (Redis).
- Roles are enforced per route. Teachers can edit attendance and marks until submitted; then only a principal can.
- Aadhaar: only the last 4 digits are modelled. Do not store full Aadhaar numbers.
- Public enquiry form: per-IP throttle uses `x-forwarded-for`, which a client can spoof. Behind a real proxy/CDN use the platform-supplied client IP and add a CAPTCHA before exposing it widely.
- Student data: Aadhaar is stored as the last 4 digits only and always returned masked; phone numbers are normalised to `+91 XXXXXXXXXX`; duplicate name + date of birth needs `confirmDuplicate`.
- Money is stored in paise as integers. Recording a payment does not move money: there is no payment gateway.

## Schools portal, subscriptions, payments, imports

Platform admin only (`platform@demo.test` in the demo): `GET/POST /api/platform/schools`, `GET/PATCH /api/platform/schools/:id` (plan, renewal date, grace days, student limit, suspend/reactivate), `PUT /api/platform/schools/:id/bank` (account number stored encrypted, shown masked), `POST /api/platform/schools/:id/go-live`. The platform team never sees a school's records (tenant routes answer 403).

A school is created _Provisioned_ with boards, a campus, the first academic year and an owner invite. It becomes _Live_ only when the checklist passes (owner set a password, board, year, classes, staff, students, fee heads, bank). While provisioned, parents and students cannot sign in. Addresses: `<slug>.school.<domain>` and `<slug>.parents.<domain>` (`ZAQSA_BASE_DOMAIN`, default `zaqsa.com`); `GET /api/public/resolve-host?host=` tells the front end which school and site an address belongs to.

Subscription (derived from `periodEnd` and `graceDays`): trial/active, then `past_due` (everything works), then `restricted` and `cancelled` (staff can read and export but not change; `read_only` 403). Parents and students keep access and can still pay. Suspending a school signs its staff out at once.

School side: `GET /api/school/status`, `GET /api/school/export`, `GET /api/audit-events`, `POST /api/classes/standard`, `POST /api/classes/:id/subjects`, `GET/POST /api/fees/heads`, `POST /api/fees/invoices`, `POST /api/exams/:id/approve` (marks must be approved before publishing; any later mark change withdraws the approval; marks cannot change while published).

Imports: `POST /api/imports/students` (CSV, checked line by line, nothing saved), `POST /api/imports/:id/commit` (once only), `POST /api/imports/:id/undo` (only while none of the students has records). CSV only; Excel files must be saved as CSV first.

Online payments: `POST /api/fees/invoices/:id/pay` (parent) creates an attempt against a **stub** order; `POST /api/webhooks/razorpay` verifies the HMAC signature (`RAZORPAY_WEBHOOK_SECRET`), processes each event id once, checks the amount, then records the payment and a ledger entry. A browser redirect never marks anything paid. Writes accept an `Idempotency-Key` header on invoice and school creation. Roles added: vice principal, admission officer, HR, reception (HR and reception have no endpoints yet).

Finance additions: `POST /api/fees/invoices/generate` bills a section or class at once (`preview:true` shows totals first; a school-wide percent plus a sibling percent, siblings found by shared guardian or guardian phone; a student already billed that title is skipped). `POST /api/fees/payments/:id/refunds` asks for a refund, `POST /api/fees/refunds/:id/decision` approves or rejects it and must be a different person (owner or principal); approval posts a negative payment and, for online payments, a negative ledger entry. No money is sent back automatically. `GET /api/fees/payments/:id/receipt` gives receipt data with a number that never changes. `POST /api/fees/reminders` e-mails overdue guardians (dry run by default, not again within the gap). `GET /api/me/invoices` lists a parent's invoices.

Authenticator sign-in: `POST /api/auth/mfa/setup|enable|disable`; once on, login needs `code` (6 digits, each code works once). It is optional per user and not yet forced for any role.

## ZAQSA core: team roles, catalog, leads, activation, support desk

ZAQSA staff have a `platformRole` (null means super admin): `super_admin`, `sales`, `finance`, `customer_success`, `support`, `product_manager`, `project_manager`, `developer`, `designer`, `marketing`. `requirePlatform([...])` in `src/server/platform.ts` guards each route; super admin passes everywhere. Demo logins: `sales@demo.test`, `support@demo.test`, `product@demo.test`. School routes now follow the roles: reading schools is open to sales, finance, customer success and support; creating or changing a school, go-live and bank details belong to customer success (bank also finance). `GET /api/platform/overview` gives counts only.

- **Catalog:** `GET /api/public/products` (public). `PATCH /api/platform/products/:key` (product manager) edits a product; only `available` products can be activated.
- **Leads (CRM):** `POST /api/public/leads` (website demo request; throttled, honeypot). `GET /api/platform/leads` and `PATCH /api/platform/leads/:id` (stage, owner, notes) for sales, marketing (read) and customer success. Stages: new, contacted, demo, proposal, won, lost.
- **Activation:** `GET/POST /api/platform/provisioning-requests`, `PATCH .../:id`. Order: requested, verifying, approved, provisioned (or rejected from any step before provisioned). Sales can start verification; only customer success approves or rejects. A school is marked provisioned only with its workspace linked. Payment alone never activates anything. It records the decision; it does not create the workspace (use `POST /api/platform/schools`).
- **Support desk:** schools: `GET/POST /api/support/tickets`, `GET .../:id`, `POST .../:id/messages` (staff only; owner and principal see all of the school's tickets, others their own; works even when the plan has lapsed; internal notes are never returned). ZAQSA: `GET /api/platform/tickets`, `GET/PATCH .../:id`, `POST .../:id/messages` (`internal:true` for a staff-only note) for support and customer success. A staff reply sets the ticket to pending; a school reply reopens it; a closed ticket takes no more messages.

Not built from the ZAQSA overview: one customer account that belongs to several organisations across products, single sign-on between product sites, per-product subscriptions and entitlements, projects and milestones for the service business, time-limited audited support access into a school, and staff invitations (team users are created by seed for now).

## Not built yet

- **Platform billing:** subscription invoices, payout runs and settlement reports for schools. The ledger table exists and collects online payments only.
- **Instalment plans, automatic gateway refunds, PDF receipts, SMS/WhatsApp reminders.**
- **Forcing MFA** for privileged roles and recovery codes; Excel (.xlsx) import, Hindi/English text, approval flows for notices and fee waivers, leave requests, offline attendance sync.
- **E-mail/SMS delivery:** mail is written to the Outbox table through `sendMail()` in `src/server/accounts.ts`; connect a provider (SES, SendGrid, ...) there and set `MAIL_PROVIDER`. No SMS yet. Needs a provider account.
- **Payment gateway** (Razorpay etc.): order creation is a stub and needs gateway keys; the signed callback is built and tested with a test secret only.
- **File uploads** (photos, documents): needs a storage choice.
- **Production setup:** switch Prisma to PostgreSQL, a shared store (Redis) for the login/reset throttle, deployment.

Teachers work only with classes they teach (timetable or class teacher) for attendance, marks and homework; the owner and principal are never limited. Rollover moves students only; it does not copy fees, exams, timetables or class teachers. Passwords are never set by the school: staff, parents and students receive an invite link. Student-role logins exist, but there are no student-facing endpoints yet.

Certificates are text only: there is no PDF, signature or school letterhead yet. Transport fees are stored on the route for information only and are not invoiced automatically; there is no live bus tracking. Deactivating or re-roling a driver takes them off their route. Homework has no file attachments or student submissions yet (no upload storage); due dates are IST days. Timetable: a teacher cannot be in two classes at once (database unique index plus a pre-check that names the clashing class); a refused save changes nothing.

Report cards count only submitted mark sheets; a subject below the exam pass mark fails the exam; ranks share on ties; results stay hidden from parents until published.

Boards and grade scales are editable defaults in the database, not an authoritative copy of each board's rules.
